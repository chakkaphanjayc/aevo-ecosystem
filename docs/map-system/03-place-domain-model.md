# Canonical Place domain model

Status: accepted domain contract; canonical write workflows remain deferred

## Why a canonical Place is necessary

The current workspace has customer_store_profiles and tracedee_places,
but neither is a safe universal identity:

- a public Store profile is an organization-controlled projection and may not
  represent an independent public location;
- a TraceDee place is useful for Trace content and moderation, but can have
  optional Store linkage and is not currently referenced by discovery,
  booking, Feed, and all map surfaces;
- OSM IDs are provider identifiers and must remain external references.

The canonical model should therefore be an Aevocado-owned Place entity. It may
represent a café, restaurant, studio, sports venue, landmark, market, park,
or another discoverable real-world location. It is not synonymous with a
company, organization, Store, branch, or booking venue.

## Conceptual entities

### Place

Stable Aevocado identity and public geographic object.

Required concepts:

- place_id: UUID generated by Aevo; never reused;
- slug: public, human-readable, unique among non-deleted Places, with
  redirect history on change;
- status: candidate, visible, limited, under_review, closed, removed, merged;
- canonical_name plus localized/display names;
- category taxonomy ID(s), not free-text-only category;
- geometry: point for discovery plus optional address/entrance geometry later;
- display address/area with provenance;
- created_at, updated_at, published_at, and version/revision;
- primary_source only as a display/provenance hint, never as identity.

The public model should not expose internal moderation notes, private contact
evidence, raw source payloads, or exact user-submitted coordinates when they
could reveal a person's private location.

### Place source link

One row per observed provider record or source assertion:

- provider: OSM, Overture, business, community, government/open dataset,
  manual admin, or future source;
- external_id and provider namespace;
- source snapshot/import run/version;
- source URL and license/attribution requirement;
- first/last observed timestamps;
- source record hash and normalized field payload reference;
- match status: unmatched, candidate, linked, rejected, retired;
- link confidence and review status.

The unique key is provider + external ID + dataset version where appropriate.
The link is not the Place primary key.

### Place revision and field provenance

Canonical fields need field-level ownership. A revision should record:

- changed field(s);
- previous and next value;
- actor/source;
- reason or submission ID;
- evidence reference;
- effective time;
- moderation decision;
- reversible revision number.

Field provenance prevents an external import from overwriting an approved
business address or an Admin-corrected name merely because the provider's
latest snapshot differs.

### Business / Branch / Venue link

The relationship is explicit and cardinality-aware:

~~~text
Organization
  -> Business/brand
     -> Store or Branch
        -> Venue / bookable resources
        -> Place link(s)
~~~

A Branch/Store may be linked to one primary Place and optionally additional
service locations. A Venue may share the same Place as its branch, but a venue
does not become a Place automatically. The link should carry:

- relationship type: operates_at, owns, manages, books_at, located_in;
- effective status and dates;
- organization/store/branch scope;
- verification state;
- source and audit metadata.

### Capability projection

Capabilities are a read projection, not Place identity:

- bookable;
- is_aevo_play_partner;
- booking route/venue reference;
- hours summary;
- availability freshness timestamp;
- commerce/order/queue affordance;
- capability source version.

The projection can be stale and must state freshness. It must not put live
resource occupancy, customer-specific prices, or booking secrets in a public
map tile.

### Community submission and edit

A submission is an immutable request:

- actor ID and app-scoped session context;
- target Place ID or null for a new candidate;
- proposed fields/diff;
- user-supplied evidence/media references;
- duplicate candidates;
- status and moderation decision;
- created/updated/resolved timestamps;
- audit and appeal metadata.

An approved submission creates a canonical revision through the command
boundary. It does not directly update a canonical table from the browser.

### Merge redirect

Merges must preserve references:

- source_place_id;
- target_place_id;
- reason, confidence, actor, evidence;
- effective time and reversible status;
- replacement slug/URL aliases.

Reads resolve redirects for a bounded period or return the target with an
explicit redirect marker. Feed, Trace stop, Save, submission, and booking
references must survive without rewriting user history in place.

## Identity and lifecycle rules

1. Generate place_id inside the trusted service.
2. Do not derive IDs from names, coordinates, OSM IDs, Store IDs, or slugs.
3. A coordinate move is a revision, not a new identity, unless review
   determines it is a different real-world entity.
4. A rename changes the display revision and may create a slug alias.
5. A business closure is not automatic deletion.
6. A source disappearance is evidence to review, not an automatic removal.
7. A merge is a domain event with a redirect, not a destructive delete.
8. A split creates new IDs only after human review and reference policy.

## Compatibility mapping

| Existing source | Initial compatibility interpretation | Migration caution |
| --- | --- | --- |
| customer_store_profiles.store_id | Candidate operates_at link from Store to Place, or a public-store projection source | Do not make Store ID the Place ID; preserve profile fields/provenance |
| tracedee_places.id | Existing TraceDee place identifier that needs a mapping to canonical Place | Keep old IDs resolvable until all Trace references migrate |
| OsmPlace.osmId | place_source_link.external_id | Never expose it as Aevo identity |
| FeedPlaceItem.id | Ambiguous legacy place-like ID | Version contract and state whether it is canonical Place ID or compatibility ID |
| venue_id / store_id in booking | Capability-domain references | Add an explicit Place link rather than replacing booking identity |

## Recommended contract fields

The first public version should be intentionally small:

~~~text
PlaceSummary
  id: Aevo UUID
  slug
  name
  localizedNames (optional)
  category
  point { latitude, longitude }
  area
  status
  verification { status, label? }
  business { organization? branch? displayName? }
  capabilities { bookable, partner, bookingRoute?, freshness? }
  attribution { sources[] }
  redirectFrom?
~~~

The contract should use nullability for missing data, never fake coordinates,
ratings, availability, or verification. A Place with no public point can be
discoverable by text/detail but must not appear in a viewport result.

## Explicit non-goals

- Replacing Store, Branch, Venue, or TraceDee domain tables in one migration.
- Letting user submissions write the canonical Place row directly.
- Treating every OSM object as an approved business listing.
- Adding arbitrary JSON fields without a field ownership policy.
- Creating a new search engine before PostGIS/text query limits are measured.

## ARCHITECTURE REVIEW REVISION (2026-09-24)

### Geometry model

Replace the point-only mental model with a geometry envelope:

| Field/concept | Meaning | V1 behavior |
| --- | --- | --- |
| canonicalGeometry | Authoritative public geometry, point/polygon/multipolygon-safe | Point and polygon-safe contract; no indoor mapping |
| displayPoint | Marker/card coordinate | Required for map-visible Places; derived or reviewed |
| labelPoint | Explicit label/annotation anchor | Optional |
| centroid | Derived analytic fallback | Never treated as a reviewed address without provenance |
| boundingGeometry | Optional extent for coarse viewport/density checks | Derived or source-provided |
| parentPlaceId | Containing Place | Optional |
| child/sub-place relation | Mall/tenant, park/facility, campus/building, venue/unit | Explicit typed relation |

Marker rendering uses displayPoint, then labelPoint, then a safe derived
centroid. Distance ranking uses an approved display/entrance point and
records the method. Viewport intersection uses canonicalGeometry or its
bounding geometry according to the query mode. Search text is independent of
geometry type. Detail can expose a geometry summary without exposing private
or overly precise coordinates.

### Explicit domain semantics and cardinality

| Domain object | Meaning and identity |
| --- | --- |
| Place | Cross-product geographic identity; Aevo UUID; may contain businesses or sub-Places |
| Organization | Tenant/legal operating scope; existing organization ID remains authoritative |
| Business | Commercial identity/brand; may operate many Branches |
| Branch | Operational business location; one primary Place before public location enablement, optional additional typed links |
| Store | Existing operational Store ID; not a geographic identity |
| Venue | Booking-domain identity; may link to one primary Place and retain its own venue ID |
| BookableResource | Booking resource under a Venue; never a direct Place identity |

One Place may contain multiple Businesses/Branches. A Branch may link to
multiple Places only through typed service/location relationships, with one
primary Place for map/detail identity. Parent/child Place relations are
allowed; V1 does not require indoor geometry.

### Thailand-first address shape

Canonical address fields are semantic, not UI labels:

~~~text
country
administrative_area_1
administrative_area_2
locality
neighborhood
street
house_number
postal_code
formatted_address
localized_names[]
alternate_names[]
~~~

The model must represent Thai and English values, aliases, transliterations,
and source-specific formatted addresses without assuming US state/city
semantics. UI labels are mapped at the presentation layer.

### Capability and live state

Place capability is a cached/static projection: booking supported, queue
supported, Play enabled, POS connected, or a public booking route. Live state
is separate: next slot, current queue, estimated wait, or live inventory.
Capability includes source and freshness; live reads come from the owning
service and are never placed in basemap/overlay/vector-tile payloads.

### Field-level provenance

Provenance is attached to a canonical field or revision, not one global source
priority:

- booking capability: booking/product domain only;
- business website: verified business, then approved Admin/community, then
  external candidate;
- geometry: reviewed source/Admin rule with geometry method;
- moderation: Aevo moderation only;
- address/name/category: field-specific approved sources.

Each value must answer source, observed time, source version, approver, and
canonical revision. A revision snapshot plus structured field provenance is
preferred to excessive normalization.

### Shared redirect resolver

Every consumer uses one bounded canonical resolver for retired/merged Place
IDs: Map, Search, Feed, Trace, Saves, business links, booking deep links, old
URLs, and analytics where appropriate. It must:

- cap resolution depth;
- detect loops;
- reject new writes using retired/merged IDs;
- never resurrect a retired ID;
- return target ID plus redirect metadata;
- preserve historical source/analytics IDs;
- support split and compensating rollback.

Foreign references do not require immediate distributed rewrites. Background
compaction may run later after the resolver preserves read/write safety.
